# Known limitations and scope gaps

This is a working portfolio demo, not fulfillment of every advanced requirement in the attached specification. The request itself is retained as REQUESTED_SPECIFICATION.txt for comparison.

- No reference image was attached. The UI follows the written navy/orange design specification; no genuine pixel comparison can be claimed.
- Only six catalog entries use bundled product photographs. The rest use original simplified SVG product illustrations. The hero uses two photographs rather than a composited studio scene. Product gallery controls enlarge one image rather than distinct views; per-variant photos and a multi-image model are absent. Homepage has one hero slide, so no carousel.
- JDBC is used rather than Spring Data JPA; custom CSS rather than Tailwind. Package/layer separation is compact rather than the full requested module hierarchy. OpenAPI is generated, but not all map-shaped schemas are richly typed DTO descriptions.
- Stripe, S3, real carrier, production tax, real refunds, and real payment processing are not implemented. All payment and fulfillment scenarios are explicitly simulations. Production profile disables the demo provider and seeding; real checkout needs another adapter.
- Seller signup/approval onboarding does not exist; admins can activate/suspend existing seeded stores. No roles editor or arbitrary seller provisioning UI. Store settings edit name only. Customer address editing/deletion and guest-cart merging are absent.
- Seller revenue chart, product rankings and order table are real. Dedicated order-status pie breakdown, product revenue drill-down, and full date-filtered CSV UI are absent. Fourth metric is average product order value, not conversion. Analytics exclude fully refunded portions; partial item returns are not supported.
- Returns apply to a whole seller portion, within 30 days of order creation, and have a simplified approve-and-refund path. There is no rejection/appeal workflow or partial quantity refund. Shipment tracking is a status progression and demo tracking id, not a timestamped carrier event history.
- Product stock/price edits work on variants. Listing version protects concurrent metadata edits; variant price changes do not have a version conflict UI. Low-stock thresholds are fixed defaults; inventory watch and in-app notifications flag sales/adjustments at or below threshold.
- Notifications are in-app via outbox. Only password-reset emails use SMTP; transactional order emails are not delivered. Outbox records track attempts/error with per-event savepoints, a five-attempt ceiling and administrator inspection. Network/database outages may roll back an entire batch for a later retry. Delivery is currently in-app only.
- Refund uniqueness prevents repeated stock restoration. Failed/cancelled coupon reservations release usage; paid cancellation/return keeps coupon usage consumed by policy. This differs from stores that restore coupon eligibility after refund.
- Sessions are local to one backend instance. Reset token hashing, forgotten-password throttling, signup abuse controls, email verification, MFA, trusted-proxy rate limiting, and security review are outstanding production work.
- Frontend unit tests cover only basic display formatting. API smoke and browser journeys provide core behavioral coverage. Standard PostgreSQL concurrency tests are included but cannot run in this environment without Docker. The execution report distinguishes actual runs from skips.
- Development reset email URL assumes localhost:8088. Non-Docker Vite users must transfer the token path to their frontend host. No production email-link origin setting is wired yet.
- No deployment has occurred. Docker Compose startup, Java 21 container execution, external SMTP delivery, and a real PostgreSQL 16 multi-connection concurrency run must be verified on a capable host before asserting full acceptance.
